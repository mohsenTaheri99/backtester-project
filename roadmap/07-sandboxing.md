# Sandboxing

If the platform ever executes code it did not write — generated by a model, or
pasted by a user — this document is the part that must not be improvised.
Written September 2026; sources at the end.

## The one thing to know first

**Python cannot be sandboxed inside itself.** This is not a matter of trying
harder. The interpreter is introspective and mutable: the object graph, frames,
tracebacks and `__subclasses__` give any running code paths back to the
interpreter's internals. Every "restricted Python" approach in the last two
decades has been escaped.

Concretely: an AST allowlist that rejects `import os` is a *useful filter* — it
catches accidents and lazy attacks, and it belongs in the pipeline — but it is
**not** a security boundary. The boundary has to be below Python: a separate
process with a restricted kernel interface, a user-space kernel, or a virtual
machine.

## Threat model

What could a hostile strategy do if it ran unconfined inside the backend?

| Target | Damage |
|---|---|
| `settings.json` | **The user's Twelve Data API key**, readable and exfiltratable |
| Other users' data | On a server, every candle file and every strategy |
| Outbound network | Exfiltrate the above; use the host as a proxy; attack third parties |
| CPU / memory | An infinite loop or a 40 GB allocation takes the service down for everyone |
| The host | Container escape, credential theft, lateral movement |
| Cost | Crypto mining, which is the normal outcome of an open execution service |

Two attackers matter, and they are different:

1. **The model, by accident.** Generated code with an unbounded `while`, a
   runaway allocation, or a stray `open()`. Common, non-malicious, and mostly
   caught by resource limits.
2. **The user, on purpose.** The "strategy description" is user input flowing
   into a code generator. Someone will write a description crafted to make the
   model emit code that reads the filesystem. Prompt-level defences do not stop
   this; only the execution boundary does.

Assume every generated artefact is hostile regardless of how the prompt was
written.

## The options, honestly compared

| Approach | Isolation | Cost / latency | Verdict |
|---|---|---|---|
| **AST allowlist in-process** | None (a filter) | Free | Use as stage 2 of the gauntlet; never as the boundary |
| `RestrictedPython` / audit hooks | Weak | Free | Same. Raises the bar for accidents only |
| **Subprocess + rlimits + seccomp** (e.g. nsjail) | Moderate | ms | Reasonable floor for a desktop app; not enough for multi-tenant |
| **Container (Docker/runc)** | Shared kernel | ~100ms | 2026 consensus: not sufficient for untrusted code on its own |
| **gVisor** | Strong (user-space kernel intercepts syscalls) | ~100-200ms start | Good multi-tenant answer; lower overhead than a VM |
| **Firecracker microVM** | Strongest (own kernel, hardware virtualisation) | ~125ms+ start | The current gold standard for untrusted code |
| **WASM / Pyodide** | Strong by construction | Slower numerics | Attractive on paper; pandas/numpy in WASM is the problem, see below |
| **One VM per tenant** | Strongest | Expensive | Only if the customer pays for it |

The 2026 consensus in the sources below is blunt: a shared kernel is no longer
considered adequate for untrusted AI-generated code. For anything multi-tenant,
the real choice is **gVisor or Firecracker**, and a plain Docker container is
not a sandbox.

### On WASM/Pyodide

Running the strategy in the *browser* under Pyodide is genuinely appealing — the
untrusted code never reaches your server, and the desktop app is already a web
view. Two obstacles: the numeric stack (pandas, numpy, backtesting.py) in WASM
is heavy and much slower on 1m data over months; and the browser is not a
capability-denied environment — Pyodide can reach JavaScript, so page data and
exposed APIs still need thinking about. Worth a prototype for level 2/3
*desktop* execution; not a server strategy.

## What the sandbox has to provide

Isolation is necessary and not sufficient. A usable execution sandbox for this
workload also needs:

- **No network.** Total, not filtered. The strategy has no legitimate reason to
  make a request; the sandbox should have no route at all.
- **Read-only filesystem**, plus one writable temp directory that is discarded.
- **Hard wall-clock limit** (30-60s for a backtest), enforced by the supervisor,
  not by the code.
- **Memory cap** sized to the dataset — a year of 1m gold is tens of MB as a
  DataFrame; a 512 MB-1 GB cap is generous and still bounds the blast radius.
- **CPU cap** and a queue, so one user's run cannot starve the rest.
- **No host mounts, no secrets in environment variables.** The API key must not
  exist anywhere inside the sandbox.
- **Data in, results out, nothing else.** The candles go in as a read-only
  memory-mapped Arrow/Parquet block; the result comes back as validated JSON. No
  shared writable state.
- **A fresh instance per run.** Never reuse a sandbox between users; state that
  survives is state that leaks.
- **Kill and report.** A run that exceeds a limit returns a clear message to the
  user ("your strategy ran longer than 60s"), not a generic 500.

## Recommended path, staged

The stages match the levels in [AI text-to-strategy](06-ai-text-to-strategy.md),
which is the point: most of them need no sandbox at all.

**Stage 0 — Levels 1 and 2 need no sandbox.** Parameter mapping executes
nothing; the declarative spec is *interpreted* by code you wrote, over a
whitelisted expression tree with no `eval`. The interpreter is the sandbox. This
is the strongest argument for the level-2 design: it removes the entire problem
rather than containing it.

**Stage 1 — Desktop level 3.** If generated Python runs on the user's own PC,
the threat model is smaller (their machine, their key, their risk) but not
empty: a malicious *shared* strategy would run with the user's privileges. A
separate process with rlimits, no inherited environment, and a warning before
running anything imported from elsewhere is a proportionate answer.

**Stage 2 — Server level 3, single tenant.** gVisor, no network, read-only
root, 60-second cap, fresh instance per run, queued. Runs on one machine; good
enough for a private beta.

**Stage 3 — Server level 3, multi-tenant at scale.** Firecracker microVMs
managed by a pool, or a commercial code-execution sandbox service. At this point
it is infrastructure with an on-call rotation, which is a real cost to weigh
against the revenue the feature brings.

## Cost and operational reality

A sandbox is not a one-time build. It brings: a pool to keep warm (or accept
cold-start latency on every run), a queue and backpressure, per-tenant quotas,
monitoring for runs that die, an abuse story for mining attempts, and a patch
cadence for the isolation layer itself. For a solo developer this is the single
largest operational commitment in the whole plan — which is the reason level 2
exists in [AI text-to-strategy](06-ai-text-to-strategy.md), and the reason
level 3 should wait for evidence that users need it.

## Checklist before any generated code runs on a server

- [ ] Execution happens outside the API process, in gVisor or a microVM
- [ ] No network route exists from the sandbox
- [ ] Filesystem is read-only except a discarded temp directory
- [ ] Wall-clock, memory and CPU caps are enforced by the supervisor
- [ ] No credentials or secrets are reachable from inside
- [ ] Sandboxes are never reused between runs or users
- [ ] Static analysis runs first (cheap rejection of the obvious)
- [ ] The lookahead audit and determinism check run before a result is shown
- [ ] Limit breaches produce a specific, honest message to the user
- [ ] Per-user quotas exist before, not after, the first abuse
